# Day 5 — Rubric

Programme-standard weights, expanded into Day 5–specific observable criteria. `scripts/grade.mjs` scores everything except Presentation (marked by hand from the learner's `NOTES.md` note) — it prints a total out of 85 and Presentation is added on top by the trainer, out of 15, for 100 overall.

| Criterion | Weight | Full marks | Partial marks | Zero marks |
|---|---|---|---|---|
| **Functionality** | 30 | All three hook files exist and pass `node --check`; the lint hook demonstrably exits `2` on a crafted lint violation and `0` on clean input; the secret-block hook demonstrably exits `2` on a crafted secret-shaped string and `0` on clean content — proven by actually invoking each hook with fabricated stdin, not just by the files existing. | One hook works correctly but another is missing or inert (e.g. secret-block always exits `0` regardless of input); the lint hook fires but its exit code is wrong (e.g. `1` instead of `2`, so Claude Code treats it as a non-blocking error rather than a block); pattern coverage in secret-block catches some but not all of the three required shapes (AWS key ID, `sk-`-style token, PEM header). | No hook files, or hooks exist but are syntactically invalid; hooks always exit `0` regardless of input (a hook that can't ever block isn't doing its job); dynamic invocation crashes instead of producing a clean exit code. |
| **Tool usage** | 25 | `.claude/settings.json` correctly wires `PostToolUse` → lint hook and `PreToolUse` → secret hook (both with a `"Write\|Edit"`-shaped matcher) and `Stop` → the stop hook (no matcher), each `command` pointing at a real file, while preserving the pre-existing `permissions` block; `.github/workflows/claude-review.yml` exists, is valid YAML, triggers on `pull_request`, and its Claude review step is both headless (`claude -p` / `--output-format json` or equivalent) and restricted to `Read`, `Grep`, `Glob` with no `Write`/`Edit`/unscoped `Bash`. | Hooks are wired but to the wrong event (e.g. lint hook on `PreToolUse` instead of `PostToolUse`, which would lint content that doesn't exist on disk yet); workflow exists and triggers correctly but the tool restriction is incomplete (e.g. `--allowedTools` present but also grants `Bash` unscoped); YAML is valid but the review step isn't actually headless (would hang waiting on a TTY in real CI). | `hooks` block missing or malformed JSON; no workflow file; workflow's Claude step has no tool restriction at all, or grants `Write`/unscoped `Bash` to an automated CI run. |
| **Code quality** | 20 | None of the three hooks throws an uncaught exception or exits an unexpected code when given malformed or empty stdin — each degrades to exit `0` on unparseable input rather than crashing; the workflow has an explicit, traceable step that converts a critical review finding into a non-zero job exit (not a comment with no build consequence). | A hook mostly handles bad input but one edge case (e.g. completely empty stdin, not just malformed JSON) isn't guarded and produces an unexpected exit code; the workflow's fail path exists but is fragile — e.g. depends on exact wording rather than a clearly parseable signal. | A hook crashes (uncaught exception) on malformed stdin; the workflow has no real fail path — a critical finding and a clean review produce the same (green) build result either way. |
| **Presentation** | 15 (hand-scored) | `NOTES.md` Assessment note is specific: names which secret patterns the scanner catches and why those three, describes exactly how the CI fail path was verified locally (the actual command/script run, the actual output seen) without needing a live PR, and names a real, specific limitation rather than a generic disclaimer. | Note present but generic ("I added hooks and a workflow and tested them") without naming the specific patterns or verification commands; mentions a limitation but it's boilerplate ("could be improved") rather than concrete. | No `## Assessment` section, or the note reads as copy-pasted model output rather than the learner's own account. |
| **Best practices** | 10 | No hardcoded API key or token literal anywhere in the committed workflow YAML — the Anthropic key is read from a named GitHub Actions secret; the pre-existing `permissions` `allow`/`deny`/`ask` lists in `.claude/settings.json` are untouched by today's edit, not overwritten or dropped while adding the `hooks` block. | A secret reference is present but inconsistently named or only partially wired (e.g. referenced in one job but hardcoded as a placeholder in another); the `permissions` block survived but was reordered or had an entry silently dropped. | A literal API key or token string committed anywhere in `.github/workflows/claude-review.yml`; the `permissions` block was deleted or replaced when the `hooks` block was added. |

**Scoring note for the trainer**: `scripts/grade.mjs` prints a per-criterion table with points earned out of 30/25/20/10 (Functionality, Tool usage, Code quality, Best practices — Presentation is excluded from its total) and a combined total out of 85. Add your hand-scored Presentation mark (0–15) to get the final mark out of 100. The programme pass mark is 60/100 overall; the script itself exits non-zero below 60/85 on its own scope as an early warning, but the authoritative pass/fail decision is the full 100-point total including your Presentation mark.

**Validated against the starting state**: this grader is checked to score at (or very near) zero and exit non-zero against Day 5's unmodified starting state (`.claude/hooks/` and `.github/workflows/` don't exist yet) — if it doesn't, the grader itself is broken and its score should not be trusted.
