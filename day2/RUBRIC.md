# Day 2 — Rubric

Programme-standard weights, expanded into Day 2–specific observable criteria. `scripts/grade.mjs` scores everything except Presentation (marked by hand from the learner's `NOTES.md` note) — it prints a total out of 85 and Presentation is added on top by the trainer, out of 15, for 100 overall.

| Criterion | Weight | Full marks | Partial marks | Zero marks |
|---|---|---|---|---|
| **Functionality** | 30 | `buildReport` still exported with the same signature; at least three other named functions extracted from its body, each under roughly 60 lines; `tests/reportBuilder.characterization.test.ts` still passes with zero snapshot changes. | One of: fewer than three qualifying extractions (e.g. only one or two); one extracted unit noticeably over the line-count guideline; characterization tests pass but only after a snapshot update (a real behavior change, partially credited down from full marks only if the change is trivial and clearly unintended, otherwise treat as failing). | `buildReport` missing, renamed, or signature changed; characterization tests fail outright; snapshots were regenerated to paper over a behavior change. |
| **Tool usage** | 25 | A new, passing unit test exists under `tests/` for at least one extracted unit (not just the pre-existing characterization test); `npm run lint` passes; `NOTES.md` has a substantive `## Assessment` note that names the specific extraction boundaries and the specific command used to verify behavior at each step (not "I checked it worked"). | New test exists but is thin (asserts one trivial case only); lint passes but with warnings that should have been addressed; `NOTES.md` note is present but generic. | No new unit test for any extracted function; lint fails; `NOTES.md` missing the `## Assessment` section entirely or it's boilerplate. |
| **Code quality** | 20 | Extracted units are meaningfully smaller and more focused than the original inline blocks (not just relocated code with no real decomposition); `buildReport` itself is substantially thinner after the refactor, orchestrating calls to the extracted units rather than still containing most of the original logic inline; `npx tsc --noEmit` (or `npm run build`) compiles cleanly. | Extraction happened but `buildReport` is still doing most of the work with only a small sliver moved out; naming of extracted functions is generic (`helper1`, `doStuff`) rather than descriptive; compiles with only cosmetic issues. | No real decomposition — functions exist but are trivial pass-throughs; `buildReport` is essentially unchanged in size; TypeScript fails to compile. |
| **Presentation** | 15 (hand-scored) | `NOTES.md` Assessment note is specific: names the actual extracted function names and the reasoning behind where each boundary was drawn, describes a concrete verification step per extraction (not one verification at the very end), and explicitly notes what was deliberately left alone (e.g. the N+1 user lookups) and why. | Note present but generic ("I extracted a few functions and ran the tests") without naming specifics; mentions verification but not per-step; doesn't mention what was deliberately out of scope. | No `## Assessment` section, or the note reads as copy-pasted model output rather than the learner's own account. |
| **Best practices** | 10 | No new dependencies added to `package.json`; the refactor didn't silently touch or "clean up" the known N+1 user-lookup pattern while doing unrelated work; commits/diff are scoped to `reportBuilder.ts` and its tests, not sprawling into unrelated files. | New dev-only dependency added that wasn't strictly necessary; N+1 pattern altered incidentally (even if for the better) without being called out as an explicit, separate decision. | New runtime dependency added; N+1 pattern silently "fixed" as a byproduct with no acknowledgment, removing it as a future exercise; unrelated files changed with no explanation. |

**Scoring note for the trainer**: `scripts/grade.mjs` prints a per-criterion table with points earned out of 30/25/20/10 (Functionality, Tool usage, Code quality, Best practices — Presentation is excluded from its total) and a combined total out of 85. Add your hand-scored Presentation mark (0–15) to get the final mark out of 100. The programme pass mark is 60/100 overall; the script itself exits non-zero below 60/85 on its own scope as an early warning, but the authoritative pass/fail decision is the full 100-point total including your Presentation mark.

**Validated against the starting state**: this grader is checked to score low and exit non-zero against Day 2's unmodified starting state (`buildReport` still one ~275-line function, no extractions, no new tests) — if it doesn't, the grader itself is broken and its score should not be trusted.
